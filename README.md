# campus-steam-exa

**Everything in this repository is synthetic. The campus, Example University, is fictional, and no
data describes a real plant.**

This repository optimizes a district steam network with
[ExaModels.jl](https://github.com/exanauts/ExaModels.jl) and
[MadNLP.jl](https://github.com/MadNLP/MadNLP.jl), on CPU and GPU. Each hour is a steady-state solve of
the network physics, and a sequence of hours is solved as one problem, coupled by the plant's ramp limit.
There are no pipe transients and no valves.

Results are published at <https://exanauts.github.io/campus-steam-exa/>.

## Reproduce

From a clone of this repository, with Julia 1.13:

```sh
julia --project scripts/run_all.jl
```

The script instantiates the `scripts` environment and runs the same steps as the
[`site` workflow](.github/workflows/site.yml). It writes the results to `site/data/`. Set
`CUDA_VISIBLE_DEVICES` to choose the GPU. A run without a GPU has not been tested.

**Time.** The site workflow builds the scenarios, the calibration and the benchmarks as three parallel
jobs and then merges them. The scenario and calibration jobs also run their independent solves on a pool
of worker processes (`SITE_WORKERS`). Run that way locally on the same kind of machine, the jobs took
5.5, 5.9 and 4.1 minutes, so the build is set by the longest job, about 6 minutes, plus a few minutes of
setup, merging and publishing. The workflow time in CI will be confirmed by its first run. `run_all.jl`
runs the three parts one after another, each with its own worker pool, and took 15 minutes locally (27
minutes without the pools). A runner without the Julia packages
installed also spends time downloading and precompiling them.

**Not regenerated by this command.** The local benchmark sweep lives in [`results/`](results) and
[`docs/gpu-notes.md`](docs/gpu-notes.md) and is not shown on the site, which shows only the solves of its
own build. These are separate runs:

| Files | Command |
|---|---|
| `results/benchmarks.csv`, `results/benchmarks_summary.json` | `julia --project=scripts scripts/site/benchmarks.jl local` |
| `results/validation*.csv` | `julia --project=validation validation/run_validation.jl` |

## Results

- **Operating scenarios, a new-building study and calibration.** See the
  [site](https://exanauts.github.io/campus-steam-exa/). Its data files are generated by the build. The
  new-building study adds one large building to the demo campus and compares four upgrade options over
  the coldest week; the case was constructed by hand to show the method, and no costs are compared. The
  network edits it uses are in [`src/expansion.jl`](src/expansion.jl).
- **CPU versus GPU, local sweep. The GPU was faster on every multi-period horizon run and slower on
  every single-period network.** The sweep was run at commit `1b2130c` on the current layout. Here the
  GPU counts as faster at a size when its median time is lower, every repeat solved on both devices,
  and its KKT residual is at most twice the CPU's; crossover means it is faster at one size and every
  larger one. At a matched tolerance of 1e-8, all five repeats solved on both devices in every case. On
  the demo campus the GPU's median was 0.19 times the CPU's at T = 24, 0.07 times at T = 168 and 0.02
  times at T = 720 (9.47 s against 426.0 s), so it crossed over at or below T = 24; shorter horizons
  were not run. At T = 24 and 168 two of the five GPU repeats were much slower than the rest, so a single
  solve there is not dependably faster. On single-period networks from 166 to 800 junctions the GPU was
  slower at every size, from 1.34 to 7.88 times the CPU time, so there was no crossover in network
  size. The machine was shared and busy during the sweep (1-minute load average 17 to 102 on 192
  logical CPUs), so all timings were taken on a loaded host. See
  [`docs/gpu-notes.md`](docs/gpu-notes.md) and [`results/benchmarks.csv`](results/benchmarks.csv).

## Limits

- This is a planning model on invented data. Its results are not predictions for any real plant.
- Each hour is a steady state. The plant ramp limit is the only link between hours, and there is no
  thermal storage or pipe inventory.
- Steam cools without condensing, and saturation is fixed at 100 C regardless of pressure, so heat loss
  and part-load behavior do not predict how a real steam network behaves.
- Steam is an ideal gas with constant specific heat. Friction factors are constants per pipe. Pump and
  compressor energy is not counted, and boilers are not modeled individually.
- Water-side pressures, return-side temperatures and flows in lightly loaded pipes are not unique at the
  optimum.
- GPU iteration counts vary between identical runs, and the cause was not isolated.

See [`docs/model-notes.md`](docs/model-notes.md) and [`docs/gpu-notes.md`](docs/gpu-notes.md).

### Not run

- Horizons between 1 and 24 hours in the benchmark sweep, so the GPU crossover in the number of periods
  is located only as "at or below T = 24".
- A full-year horizon did not finish: T = 8,760 was attempted once per device on the earlier layout and
  neither solve completed ([log](results/logs/benchmarks_year_attempt.txt)). It was not run on the
  current layout.
- Calibration on the GPU with longer records. The site build attempts the GPU only at 25 tags and
  1 month, so the 3-month and 6-month cases were not run on the GPU in any recorded build.
- Single precision, a multi-threaded CPU, the augmented KKT system on the GPU, and asynchronous cuDSS in
  the strict runs.
- Many outage cases solved as one batch, and networks much larger than this campus.

## Citation

The physics follows:

> Hari, Srinivasan, Zlotnik, Sundar, Ewers, "Optimization of District Heating Network Parameters in
> Steady-State Operation", [arXiv 2404.18868](https://arxiv.org/abs/2404.18868).

The reference implementation is
[ThermalModels.jl](https://github.com/lanl-ansi/ThermalModels.jl). This repository is a reimplementation
and copies no upstream code.
